# Обновления BotCRM через Tailscale Funnel

Панель и API переключаются между двумя наборами контейнеров (`blue` / `green`). PostgreSQL, Redis, MinIO и Tailscale продолжают работать. Публичный адрес и внутренний адрес `http://api:4100/api/v1` для контентных ботов сохраняются.

## Обычное обновление

На уже подготовленном сервере:

```bash
cd /opt/botcrm
git pull --ff-only
npm run prod:deploy -- "$(git rev-parse --short=12 HEAD)"
```

Скрипт требует чистый checkout и не допускает параллельные выкатки. Он собирает образы с тегом коммита, применяет миграции, запускает неактивный набор и ждёт готовности API и веба. Затем проверяет новый транспорт через временный порт Funnel `10000`, плавно переключает Caddy и основной порт `443`. Временный порт убирается, старая версия остаётся для завершения соединений и отката. Состояние хранится в игнорируемой папке `.runtime/`.

Старый worker корректно завершает текущие задачи перед запуском нового. Очередь остаётся в Redis; обработка задач на время этой смены может задержаться. Обрывы внешнего Funnel/DNS и неработающий интернет этим механизмом не устраняются.

При ошибке проверки восстанавливаются прежние маршруты и worker. Выкатка прерывается, если порт `10000` уже занят. Образы и тома других Compose-проектов скрипт не меняет. Не используйте `docker compose down`, `down -v` или старый `prod:up` для обычного обновления работающего приложения.

## Первое переключение существующей установки

У работающей установки файл `infra/tailscale-serve/serve.json` уже смонтирован в Tailscale. Нельзя сначала заменить его новым шаблоном: новый `edge` ещё не запущен. Подготовьте отдельный checkout нового коммита, подключите к нему существующие `.env.production` и `.runtime`, затем запустите скрипт с `BOTCRM_SERVE_CONFIG_FILE`, указывающим на **существующий смонтированный файл**. Новая версия и маршрутизатор будут подготовлены до смены этого файла. Только после успешной проверки обновите основной checkout до того же коммита.

После первой миграции `serve.json` совпадает с новым шаблоном. Его последующие изменения тоже требуют подготовленного транспорта. Не меняйте его вручную во время выкатывания.

## Передача IP и ограничения запросов

Funnel завершает TLS и передаёт IP клиента через PROXY protocol v2 на отдельный listener Caddy `8081`. Caddy принимает эти сведения только с адреса контейнера `botcrm-tailscale-1`, определённого через Docker inspect, и самостоятельно перезаписывает HTTP-заголовки адреса. Присланные посетителем `X-Forwarded-For`, `Forwarded`, `X-Real-IP` не становятся доверенным IP. Административный API Caddy доступен только внутри его контейнера на loopback; порты контейнера наружу не публикуются.

Ограничения входа действуют по IP и паре IP + аккаунт. Чужие попытки с другого IP больше не блокируют владельца аккаунта. Это сохраняет обычный вход по паролю, но не даёт полной защиты от распределённого подбора с множества адресов. Прежние переменные `LOGIN_ROUTE_RATE_LIMIT_EMAIL_*` и `LOGIN_RATE_LIMIT_EMAIL_MAX` больше не используются; используйте `LOGIN_ROUTE_RATE_LIMIT_PAIR_*`.

У Content API сначала применяется `BOT_CONTENT_RATE_LIMIT_IP_MAX` (по умолчанию 3000 запросов в минуту), затем отдельный лимит токена. Смена неверного токена не обходит первый лимит. Header и Bearer с одним токеном расходуют один и тот же счётчик.

## Совместимость миграций и откат

Онлайн-выкатка допускает только миграции, совместимые одновременно со старой и новой версией: сначала добавление полей, затем отдельный релиз с переходом на них, и только в следующем релизе удаление старого. Деструктивные изменения требуют отдельного плана обслуживания. Автооткат маршрутов не отменяет SQL-миграции.

Последняя версия записана в `.runtime/release.json`. Предыдущие API и web остаются запущенными до повторного использования их слота. Для отката на исправный коммит запустите `prod:deploy` из его checkout; обычные проверки применяются и при откате. Не удаляйте `.runtime` или образы предыдущего релиза до проверки новой версии.

При перезапуске всей инфраструктуры сначала поднимите PostgreSQL, Redis и MinIO, затем восстановите активные контейнеры и `edge`, и после этого Tailscale. На действующей установке они имеют `restart: unless-stopped` и запускаются Docker автоматически.
